# 武大通知聚合 · WHU Notice Hub 总体设计

> 版本 v0.1 ｜ 2026-11-21 ｜ 面向：武汉大学在校生（首发计算机学院，架构上支持全校）
> 本文是"整体构思 + 可落地方案"：先讲清问题与边界，再给架构、数据模型、采集规则、重要性判定、推送策略、合规风险与 MVP 路线。所有信源结构均已实测（见 §3 与 `config/sources.example.yaml`）。

---

## 0. 一句话定义

把散落在武大官网、信息公开网、计算机学院、研究生院等 20+ 个栏目里的通知公告，做成**一个入口**：新公告 30 分钟内入库 → 自动去重合并 → 抽取出"谁该看、什么时候截止、要做什么" → 按个人画像排序 → 邮件/IM/网页推送，原文链接可追溯。

核心主张不是"再做一个抓取网页的网站"，而是三件事：

1. **不漏**：翻页水位 + 全量兜底 + 失败告警，而不是只看首页 10 条。
2. **降噪**：跨站转载合并、公示/讲座/日常通知分级，只把"和你有关且要行动"的推给你。
3. **可执行**：截止日期、适用对象、材料清单、异议期从正文里抽出来，直接进日历/待办。

## 1. 问题定义

学生真实遇到的痛点，按严重程度排序：

| # | 痛点 | 具体表现 | 设计上的对应 |
|---|---|---|---|
| 1 | 关键信息被淹没 | 推免细则、奖学金、考试安排混在公示、讲座预告、会议通知里 | 重要性评分 + 分类 + 订阅过滤 |
| 2 | 截止时间藏在正文深处 | "请于 6 月 1 日 9:15 到四楼报到"，列表页只看到发布日期 | LLM/规则抽取 deadline + 日历视图 |
| 3 | 附件才是重点 | 名额分配、名单、承诺书模板都在 PDF/docx 附件里 | 附件下载 + 文本抽取（P1） |
| 4 | 同一通知多处转载 | 学院转发学校、信息公开网再转一次，重复刷屏 | 跨源聚类去重 |
| 5 | 公告会被修改 | 延期、补充说明、名单更正，链接不变 | 版本追踪 + "已更新"标记 |
| 6 | 不知道该看哪个网站 | 官网/信息公开/学院/研究生院/本科生院/后保/图书馆/就业… | 统一信源目录 + 一个时间线 |
| 7 | 只刷首页导致漏抓 | 官网首页只显示 10 条，一天发 12 条就漏 | 增量水位 + 每日全量回扫 |

## 2. 用户与场景

**MVP 用户**：你自己（计院学生）+ 同班同学，单实例、单校、低并发。

| 场景 | 用户动作 | 系统行为 |
|---|---|---|
| 每日扫一眼 | 早 8:30 看邮件/网页 | 日报：昨日高优新增 + 未来 7 天截止提醒 |
| 怕错过 | 订阅"推免/奖学金/考试"关键词 | 命中且分数 ≥ 阈值 → 立即推送 |
| 班委转发 | 点"生成转发卡片" | 标题 + 一句摘要 + 截止时间 + 原文链接，复制即发群 |
| 临时查 | 搜"缓考""补选" | 全文检索（含附件文本） |
| 事后追溯 | "上次那个停水通知是什么时候" | 归档 + 按栏目/时间筛选 |

**明确不做**（至少在 MVP）：替学生登录、抓取成绩/课表、抓微信群/QQ 群消息、做论坛/社区。

### 3.2 三条决定架构的实测发现

1. **80% 的站点是同一套 CMS（博达 VSB）**：URL 形如 `/info/{treeid}/{newsid}.htm`、`content.jsp?wbtreeid=..&wbnewsid=..`、详情页容器是 `#vsb_content` / `.v_news_content` / `div.article`。
   → **一个通用适配器 + 每源少量配置** 就能覆盖，不需要一网站一爬虫。

2. **列表页不是严格按日期倒序**。实测官网首页顺序：`11-20, 11-07, 11-04, 11-02, 11-06, 10-22…`（置顶/补发会插入旧日期）。
   → **绝对不能用"遇到旧日期就停止翻页"的算法**，否则会漏抓。必须用"已知链接/ID 集合差集"做水位。

3. **学生/教工通知栏被 CAS 拦截**（302 到 `cas.whu.edu.cn`），且 `robots.txt` 在主站 404、子站 403（有 WAF）。
   → 自动抓取只做**公开页面**；登录源不碰账号，最多支持"用户自己粘贴 cookie 的本地导入"，且默认为关闭的可选插件。

### 4.2 一次抓取的完整生命周期

```
sources.yaml
   │
   ├─▶ 1. 拉列表页（第 1 页 + 视情况翻页），得到 [{title, url, date, publisher}]
   ├─▶ 2. url 规范化 → url_hash，与库中已有 url_hash 做差集 = 新条目
   ├─▶ 3. 对新条目抓详情（限速 1 req/s/host）→ 标题/发布时间/正文/附件
   ├─▶ 4. 正文转 Markdown，算 content_hash + simhash
   ├─▶ 5. 指纹与近 7 天同源/跨源条目比对 → 判定 新增 / 转载(聚类) / 更新(版本+1)
   ├─▶ 6. 规则抽取 → 置信度不足的字段交 LLM 补 → 打分
   ├─▶ 7. 入库（notices / notice_versions / attachments / crawl_runs）
   └─▶ 8. 命中订阅规则且分数达标 → 推送（deliveries 唯一约束保证不重复发）
```

**关键设计原则**：每一步幂等、可重跑。抓到一半失败，下次重跑不产生脏数据；某源改版不影响其他源和历史数据。

## 5. 采集层设计

### 5.1 适配器协议（一个抽象，两种引擎）

```python
class Adapter(Protocol):
    code: str
    def list_pages(self, run: CrawlContext) -> list[list[RawItem]]: ...
    def fetch_detail(self, item: RawItem) -> Detail: ...
    def health_check(self, html: str) -> None:  # 结构漂移检测
        ...
```

- `VsbAdapter`：覆盖博达 CMS，行为完全由 YAML 的 selector 驱动（官网、计院、研究生院、绝大多数部处）。
- `TableAdapter` / `JsonAdapter`：少数非博达站点（若出现 JSON 接口，直接对接，最省事）。
- `engine: http | browser`：默认 `http`（实测官网正文是服务端渲染，不需要浏览器）；只有确认为 JS 渲染的源才降级 `browser`（Playwright），并单独限速。

### 5.2 配置驱动（示例见 `config/sources.example.yaml`）

一条信源配置回答 5 个问题：**从哪抓、怎么翻页、怎么取字段、怎么进详情、多久抓一次**。

```yaml
- code: cs_whu
  name: 计算机学院·通知公告
  level: college
  list:
    url: https://cs.whu.edu.cn/xwdt/tzgg.htm
    pagination: { mode: path_desc, template: "https://cs.whu.edu.cn/xwdt/tzgg/{n}.htm", max_page: 79, backfill_pages: 2 }
  items:
    xpath: "//li[a[contains(@href,'/info/') or contains(@href,'content.jsp')]]"
    fields: { title: "./a/p", url: "./a/@href", published_at: "./a/span" }
  detail:
    title: "//h2 | //h1"
    published_at: "//*[contains(text(),'发布时间')]"
    content: "//div[@id='vsb_content'] | //div[contains(@class,'article-content')]"
    fallback: readability
  weight: 80          # 源基线权重（院系 > 校级通用？见 §7.2）
```

新增一个学院/部处 = 复制一段 YAML + 跑一次 `crawl --dry-run` 校准 selector，**不需要改代码**。这是项目能长期维护的关键。

### 5.3 增量与翻页算法（重点）

```python
def crawl_source(src):
    known = db.recent_url_hashes(src.code, days=90)     # 集合，O(1) 判断
    new_items, pages = [], 0
    for page_url in iter_pages(src, max_pages=src.backfill_pages):
        items = parse_list(page_url)
        if src.health_check(items) is BAD:               # 空列表/字段缺失率突增
            alert(f"{src.code} 疑似改版"); break
        page_new = [i for i in items if norm(i.url).hash not in known]
        new_items += page_new
        pages += 1
        if not page_new and pages >= 1:                  # 整页全已知 → 停止（增量模式）
            break
    return new_items
```

配套两条兜底：

- **每日 03:00 全量回扫最近 5 页**：防止"某天站点故障漏抓"和"补发旧日期公告"（实测官网确实存在补发到中间位置的条目）。
- **首页 HTML hash 监控**：hash 没变则跳过整轮，省 90% 请求；同时把"hash 变了但解析出 0 条新条目"作为**强告警信号**（大概率改版）。

日期处理：列表只到"天"，正文可能有精确时间；**拿不到日期时用 first_seen 兜底并标 `date_inferred=1`**，前端显示"约"。

### 5.4 礼仪式抓取（必须遵守）

| 项 | 策略 |
|---|---|
| 频率 | 每 host 1 req/s 串行，单轮总请求上限 200；增量每 15–30 min，全量每日 1 次夜间 |
| UA | `WHUNoticeHubBot/0.1 (+联系邮箱)`，不伪装浏览器用于绕过限制 |
| robots | 实测主站 404、子站 403（WAF）；**无明确许可时按最保守解读**：只抓公开通知页，不抓用户数据 |
| 失败 | 超时 15s，重试 3 次指数退避；连续 3 轮失败 → 告警并标记源降级 |
| 缓存 | 列表页 30 min 内不重复请求；详情页永久缓存原始 HTML 快照（便于回溯改版） |

### 5.5 结构漂移的工程化防御

- 每个源保存 1–2 份 **golden fixture**（真实 HTML 快照）→ pytest 跑解析，selector 一改就红。
- 运行时三指标：`items_count`、`date_parse_rate`、`title_nonempty_rate`；任一跌破阈值（如条目 0 条、日期解析 <80%）→ 该源标 `degraded` + 发告警，**不阻塞其他源**。
- 详情正文优先用 **readability（trafilatura）自动抽取**，selector 只做覆盖/纠偏。这样站点小改版不会立刻崩。

## 6. 处理层：规范化、去重、变更

### 6.1 URL 规范化（去重的第一道闸）

去掉 `utm_*`、`from=`、`#fragment`，统一 `http→https`、统一 host 小写，相对路径按 base_url 解析。得到 `url_hash = sha1(canonical_url)`，**唯一索引**，天然幂等。

### 6.2 三层去重

| 层 | 方法 | 解决什么 |
|---|---|---|
| L1 同源同页 | `url_hash` 唯一约束 | 重复抓取 |
| L2 跨源转载 | `title_norm`（去空格/标点/全半角、"关于…的通知"模板归一）+ 7 天窗口 + 正文 simhash 汉明距离 ≤ 6 | 学院转发学校通知 |
| L3 同一事件多公告 | 标题相似度 + 发布时间接近 + 关键词聚类（如"推免"细则/名单/复试通知） | 一个事件刷 5 条，合并成一组展示 |

L2/L3 **不删数据**：保留每条源记录（可追溯），只是展示层折叠成"主条目 + 其他来源 N 个链接"。

### 6.3 变更追踪（容易被忽略但很有用）

公告存在"发布后修改"：延期、补充、名单更正。

- 每次重抓详情页算 `content_hash`；变了 → 写 `notice_versions`，主表标 `status=updated`，并生成一行变更摘要（`difflib` 的段落级 diff，可选再让 LLM 概括"截止时间由 X 改为 Y"）。
- 推送策略：`updated` 且改动涉及 deadline/金额/名单 → 推一条"⚠️ 通知有更新"。

## 7. 理解层：从"文本"到"可行动"

### 7.1 抽取目标（统一 JSON Schema）

```json
{
  "category": "招生|教务|考试|奖助|竞赛|科研|人事|生活服务|讲座|公示|其他",
  "audience": ["本科生", "研究生", "博士生", "教师", "党员", "2027届"],
  "summary": "≤80 字，说清发生了什么",
  "deadline": { "date": "2026-06-01", "time": "09:15", "kind": "报名|材料提交|异议|活动" },
  "action_items": ["6/1 9:15 前到工学部计算机学院四楼报到", "提交纸质材料一式两份"],
  "importance": 7,
  "sensitive": false
}
```

实测样例（真实公告《计算机学院 2026 年第三批次博士入学综合考核工作通知》）：

```json
{ "category": "招生", "audience": ["博士生"], "importance": 8,
  "summary": "学院第三批次博士综合考核 6 月 1 日进行，计划招生 11 人，含笔试与面试。",
  "deadline": { "date": "2026-06-01", "time": "09:15", "kind": "材料提交" },
  "action_items": ["资格审查需带学历学位证书原件", "准备 8 分钟科研经历 PPT", "现场缴纳考核费 180 元"] }
```

### 7.2 打分公式（规则打底，LLM 修正）

```
score = clamp(
    0.30 * source_weight        # 源基线：院系 80 / 校级 70 / 部处 75 / 转载 40
  + 0.25 * category_weight      # 推免·考试·奖助·选课 0.8+；讲座·公示 0.3–0.5
  + 0.20 * urgency              # 距 deadline 越近越高；已过期 → 0
  + 0.15 * audience_match       # 与用户画像（院系/年级/身份）匹配
  + 0.10 * keyword_hit          # 用户订阅关键词
  + 0.10 * llm_judgement        # LLM 0-10 分转 0-1，判"是否需要我采取行动"
) * 100
```

- **规则先行**：deadline/受众/分类能正则+词典解决就不调模型（快、免费、可解释）。
- **LLM 只做"填空 + 纠偏"**：摘要、行动项、模糊时间（"本周五前""下周三"）、判断是否真的需要行动。
- **成本控制**：按正文前 3000 字 + 标题 + 源信息组 prompt；模型结果按 `content_hash` 缓存；同一篇只调一次；失败降级为规则结果，绝不阻塞入库。

> 直觉校验：`importance` 不是"重要程度"的玄学，而是**"这条通知会不会改变你接下来两周要做的事"**。推免细则 = 高；讲座预告 = 低；停水通知 = 中（但时效强）。

### 7.3 敏感内容红线

公示类公告常含**姓名、学号、成绩排名**（如"拟录取名单公示"）。策略：

- 只入库"这是一条名单公示 + 异议期 + 原文链接"，**不抽取、不索引、不推送个人姓名列表**；
- 附件（PDF/Excel 名单）默认不做全文进搜索；确需解析时仅本地缓存，前端只显示"附件含名单，请到原文查看"。

| `sources` | 信源注册表 | `code` PK、`config_json`（YAML 展开）、`weight`、`enabled` |
| `notices` | 通知主表 | `url_hash` UNIQUE、`title`、`published_at`、`summary`、`content_md`、`content_hash`、`simhash`、`deadline_date`、`audience_json`、`action_items_json`、`importance`、`status`(new/updated/archived) |
| `notice_versions` | 变更历史 | `(notice_id, content_hash)` 唯一，存 diff 摘要 |
| `attachments` | 附件 | `sha256`、`mime`、`local_path`、`text_excerpt` |
| `clusters` / `cluster_members` | 事件聚类 | 主条目 + 成员，处理转载/相关系列 |
| `crawl_runs` | 每轮抓取审计 | 页数、新增/更新/错误数、耗时、状态 |
| `subscriptions` | 订阅规则 | `rules_json`（关键词/来源/类别/受众/最低分）、`channel`、`quiet_hours` |
| `deliveries` | 推送流水 | `UNIQUE(notice_id, subscription_id)` 保证不重复发 |

**为什么 SQLite 起步**：单用户、日增几百条，SQLite（WAL）+ FTS5 全文检索完全够；迁移到 Postgres 只是换 DSN + 几个类型（JSONB/GIN）。不要一开始上微服务和消息队列。

## 9. 分发层

### 9.1 三个出口

| 出口 | 内容 | 技术 |
|---|---|---|
| Web 时间线 | 全部通知、筛选（来源/类别/只看有截止/只看未读）、日历视图、搜索 | FastAPI + Jinja2 + HTMX（避免前端工程化成本） |
| 邮件日报 | 每天 08:30：昨日新增高优 + 未来 7 天截止 + 本周讲座 | SMTP（QQ/163 邮箱授权码即可） |
| 即时推送 | 命中订阅且 score ≥ 75 → 立即推 | 飞书/企业微信/钉钉群机器人 Webhook（最省事）；备选 Bark / Server酱 / Telegram |

**明确不做个人微信**：没有官方 API，第三方协议号封号且违规。要么走群机器人，要么走"邮件 + 网页"。

### 9.2 推送纪律（决定用户会不会关掉它）

- **默认少推**：日报兜底，即时推送只在"高优 + 命中订阅"时触发。
- 静默时段 23:00–07:30；同一通知终身只推一次（`deliveries` 唯一约束）。
- 每个通道每日上限（如 10 条），超限合并进次日日报。
- 卡片固定四行：`标题` / `一句话摘要` / `⏰ 截止 6/1 09:15` / `原文链接`。
- 订阅规则支持"只看这些来源"和"屏蔽这些关键词"（如 `讲座`、`公示`）。

### 9.3 订阅规则示例

```json
{ "keywords": ["推免", "奖学金", "缓考", "选课", "实习"],
  "sources": ["whu_main", "cs_whu", "gs_whu"],
  "categories": ["招生", "教务", "考试", "奖助"],
  "audience": ["本科生"],
  "min_score": 70,
  "quiet_hours": "23:00-07:30",
  "channel": "email+feishu" }
```

## 10. 技术选型与部署

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.12 | 抓取/解析/LLM 生态最好 |
| HTTP | `httpx`（异步、超时/重试友好） | 比 requests 更适合并发限速 |
| 解析 | `lxml` + `trafilatura`（readability） | lxml 快；trafilatura 抗改版 |
| 校验 | `pydantic` v2 | 字段缺失/类型错误早暴露 |
| 存储 | SQLite（WAL + FTS5）→ Postgres | 零运维起步 |
| ORM | SQLAlchemy 2.0 + Alembic | 迁移可控 |
| 调度 | APScheduler（进程内）→ arq/Redis | MVP 不需要独立 worker |
| Web | FastAPI + Jinja2 + HTMX | 一个进程搞定 API + 页面 |
| 浏览器兜底 | Playwright（可选依赖） | 只给 JS 渲染源用 |
| 附件 | `pypdf` / `python-docx` / `openpyxl` | 环境已自带 python-docx、openpyxl |
| LLM | OpenAI 兼容接口（DeepSeek / 豆包） | 便宜、可换供应商、可离线降级 |
| 部署 | Docker Compose（app + db + cron）+ 单机 1C2G | 校园项目成本 ≈ 0–30 元/月 |

**部署形态**：一台能访问外网的小机器（或校园网内闲置服务器）。若部署在校内网，注意 `ugs.whu.edu.cn` 等域名解析可达性（实测本机 DNS 曾失败）。域名 + Nginx/Caddy 反代可选，MVP 用 `localhost:8000` 足够。

## 11. API 设计（MVP）

```
GET  /api/notices?since=2026-11-01&source=cs_whu&category=招生&min_score=70
     &has_deadline=true&q=推免&page=1&size=20
GET  /api/notices/{id}                 # 详情（含附件、版本历史、聚类成员）
GET  /api/digest?date=2026-11-21       # 日报 JSON（邮件渲染复用）
GET  /api/calendar?from=2026-11-21&to=2026-12-05   # 按 deadline 排的日历
POST /api/subscriptions                # 新建/更新订阅规则
POST /api/notices/{id}/read            # 已读标记
POST /api/admin/crawl/{source_code}    # 手动触发（带 token）
GET  /healthz                          # 存活 + 各源最后成功时间
```

响应统一 `{code, message, data}`；列表项固定含 `{id, title, source_name, published_at, summary, deadline, importance, url, is_read}`。

## 13. 质量保障与可观测性

### 13.1 四个黄金指标

| 指标 | 目标 | 用途 |
|---|---|---|
| 入库时延（公告发布 → 入库） | P95 ≤ 30 min | 决定"会不会漏"的产品承诺 |
| 解析成功率 | ≥ 99% | 改版第一信号 |
| 漏抓率（抽样 100 条人工核对） | ≤ 2% | 翻页水位是否正确 |
| 重复推送率 | 0 | `deliveries` 唯一约束兜底 |

### 13.2 告警（发给自己的邮箱/IM）

- 某源连续 3 轮失败 → "源挂了"
- 首页 hash 变了但新增 0 条 → "疑似改版，请校准 selector"
- 连续 24 h 全校 0 条新增 → "大概率整体故障"
- 日报发送失败 / LLM 调用连续失败 → 降级通知

### 13.3 测试

- `tests/fixtures/*.html`：每个源 1–2 份真实快照（可从实测页面直接保存）。
- 单测覆盖：列表解析、详情解析、日期多格式、URL 规范化、simhash 去重、打分边界。
- 每周一次 `crawl --dry-run` 与线上对比条目数，人工抽检。

## 14. 合规与风险

| 风险 | 具体 | 应对 |
|---|---|---|
| robots/站点条款 | 主站无 robots（404），子站 403（WAF） | 只抓公开通知，低频串行，UA 明示身份，不做压力测试式抓取 |
| 账号与登录 | CAS 统一认证 + 可能双因子 | **不接触账号密码**；登录源默认不接入 |
| 个人信息 | 公示名单含姓名/学号/成绩 | 不抽取、不索引姓名列表；只存"公示存在 + 原文链接" |
| 版权 | 通知正文有著作权 | 站内展示摘要 + 原文链接，不整篇镜像；附件仅本地缓存供检索 |
| 站点改版 | 博达模板常调整 | 配置化 + readability + golden fixture + 漂移告警 |
| 稳定性 | 单机故障即全挂 | SQLite 每日备份；抓取失败不影响历史数据 |
| 使用边界 | 非官方、非商业、校内自用 | README 明确声明"信息以官网原文为准"，不做招生/录取结论 |

## 15. 路线图（4 周 MVP）

| 周 | 交付 | 验收标准 |
|---|---|---|
| W1 | 骨架 + 博达适配器 + 官网/计院两源 + SQLite + CLI（`crawl`/`list`） | 能稳定抓到两源新公告，条目与页面一致，无重复 |
| W2 | 详情正文/附件、去重、变更追踪、邮件日报、静态 Web 时间线 | 每天早上收到一封可读的日报；网页能按来源/日期筛选 |
| W3 | 研究生院 + 2 个部处；规则抽取（分类/受众/日期）+ LLM 摘要与 deadline + 打分 | 100 条抽样中 deadline 抽取准确 ≥ 85%，重要通知排序符合直觉 |
| W4 | 订阅规则、飞书/企微推送、监控告警、Docker 部署、备份 | 命中订阅 5 分钟内收到推送；连续 7 天无严重告警 |
| P2 | 附件全文检索、公众号人工导入、事件聚类、移动端、多用户 | 按需迭代 |

**最小可用闭环（建议第一版就跑通）**：官网 + 计院两源 → SQLite → 每天一封邮件日报。这已经能解决 80% 的"漏通知"问题，不必等 LLM 和 Web 都做完。

## 16. 关键决策记录（ADR 摘要）

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| 1 | 配置化适配器，不写一网站一爬虫 | 每站一个脚本 | 20+ 源，维护成本是项目死因 |
| 2 | readability 为主，selector 为辅 | 纯 CSS/XPath | 站点改版频繁，selector 极脆 |
| 3 | 用 URL/ID 差集做增量，不用日期截断 | 遇到旧日期就停 | 实测列表非日期单调，会漏抓 |
| 4 | 不做登录抓取 | 模拟 CAS 登录 | 合规风险 + 验证码/双因子不稳 + 账号安全 |
| 5 | SQLite 起步，不上队列 | Postgres+Redis+Celery | 日增几百条，过度设计 |
| 6 | 规则先打底，LLM 做增强 | 全靠 LLM | 成本、延迟、可解释性；LLM 挂了系统不能挂 |
| 7 | 少推 + 日报兜底 | 逐条实时推 | 推送噪音是订阅类产品第一杀手 |
| 8 | 公示类不抽取个人信息 | 全量解析名单 | 个人信息保护法 + 伦理 |

## 17. 待确认（影响后续实现）

1. **推送首选通道**：邮件 / 飞书 / 企业微信 / 其他？（决定 W2–W4 的优先级）
2. **覆盖范围**：只做计算机学院 + 校级，还是本学期就扩到全校院系？（决定信源目录和权重设计）
3. **是否需要登录后的通知**（智慧珞珈/信息门户）？若需要，建议做"用户本地导入 cookie"的可选插件，不做账号托管。
4. **部署位置**：自己的电脑常开 / 校园网服务器 / 云主机？（决定 Docker 方案和访问可达性）
5. 是否需要**多用户**（给同学一起用）？若需要，W4 之后加账号体系与订阅隔离。
